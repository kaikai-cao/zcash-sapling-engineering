## 1. 底层密码学参数（先把“点有多大”定义清楚）

Sapling 使用 **BLS12-381** 曲线、**Groth16** 证明系统、**R1CS → QAP** 电路表示。

### 1.1 域与标量

| 对象 | 定义 | 位宽 | 字节 |
|---|---|---:|---:|
| 基域 Fq | BLS12-381 素数域（坐标所在域） | 381 bit | 48 B |
| 标量域 Fr | BLS12-381 标量域（指数/系数所在域，等于 r 阶） | 255 bit | 32 B |
| G2 的 Fq2 元素 | 2 个 Fq 数 | 762 bit | 96 B |

`Fr` 的 255 bit 决定 MSM 的标量窗口切块数（见 §5.2）。

### 1.2 椭圆曲线点的大小（两种编码）

| 点类型 | 未压缩 (uncompressed) | 压缩 (compressed) | 说明 |
|---|---:|---:|---|
| G1 affine (x,y) | 2 × 48 = **96 B** | 1 × 48 = **48 B** | 一个坐标 + 3 个标志位 |
| G2 affine (x,y) | 4 × 48 = **192 B** | 2 × 48 = **96 B** | 两个 Fq2 坐标 |
| G1 projective (X,Y,Z) | 3 × 48 = 144 B | — | 运行时中间量 |
| G2 projective (X,Y,Z) | 6 × 48 = 288 B | — | 运行时中间量 |

> 关键结论：**参数文件用“未压缩”编码（96/192 B），而序列化证明用“压缩”编码（48/96 B）。** 这是为什么参数文件 48 MB、而证明只有 192 B 的直接原因。

### 1.3 运行时 Rust 类型布局（`size_of`，实测）

| 类型 | size_of | align_of | 与上面编码的关系 |
|---|---:|---:|---|
| `G1Affine` | 104 B | 8 | 96 B 坐标 + 8 B 对齐填充 |
| `G2Affine` | 200 B | 8 | 192 B 坐标 + 8 B 填充 |
| `G1Projective` | 144 B | 8 | 3 × Fq |
| `G2Projective` | 288 B | 8 | 3 × Fq2 |
| `Scalar` (Fr) | 32 B | 8 | |
| `Exponent<Scalar>` | 40 B | 8 | enum 标签 + 32 B 位表示 |
| `Vec<T>` 头部 | 24 B | 8 | ptr + len + cap |
| `Arc<Vec<T>>` 句柄 | 8 B | 8 | |

来源：`experiments/raw/csv/sapling_runtime_type_sizes_20261016.csv`。

### 1.4 用到的算法清单

| 阶段 | 算法 | 复杂度/规模 |
|---|---|---|
| 电路 → R1CS | Bellman `ConstraintSystem` 合成 | O(#constraints) |
| R1CS → QAP | 拉格朗日插值，用 **逆 FFT (IFFT)** 与 **陪集 FFT (coset FFT)** 计算 A、B、C、H 多项式 | O(N log N) |
| 多项式的 H 计算 | 陪集上 A·B − C，再除以 Z_H，再做 **逆陪集 FFT (icoset FFT)** | O(N log N) |
| 多标量乘 (MSM) | **Pippenger 桶方法（bucket method）+ 固定窗口 c**，窗口间用倍点合并 | O(n·c + 2^c) 每窗口 |
| 桶求和 | **Summation-by-parts**（部分和嵌套） | O(buckets) |
| 证明组装 | 标量乘/加（G1、G2） | O(1) |
| 验证 | **Groth16 pairing product**（多个 Miller loop 可批处理） | 常数对数量 |

## 5. MSM 逐步细化（报告的核心）

MSM（多标量乘）是 Sapling Groth16 证明里最大的一块计算。一次 Spend 证明有 **8 次** `multiexp` 调用。

### 5.1 算法（`vendor/bellman/src/multiexp.rs`）

固定窗口 Pippenger 桶方法：

1. **选窗口 c**：若标量数 n < 32，取 c = 3；否则 c = ⌈ln(n)⌉。
2. **桶数**：每个窗口 `2^c − 1` 个桶。
3. **窗口切块数**：标量 255 bit，chunk 数 = ⌈255 / c⌉。
4. **指数预处理**：每个标量转成 `Zero` / `One` / `Chunks(Vec<u64>)`（`Exponent<Scalar>`，40 B/个）。
5. **每个 chunk**（可并行）：
   - 分配桶数组 `vec![identity; 2^c − 1]`（`G1Projective` 144 B 或 `G2Projective` 288 B）；
   - 遍历指数，把对应基点 `add_assign` 进桶（bucket fill）；
   - **summation-by-parts** 反向累加桶（bucket reduce），每次迭代两次群加；
   - 得到该 chunk 的部分和。
6. **合并 chunk 结果**：从高位到低位，每段先做 c 次倍点（double），再加该 chunk 结果。
7. **单值/零指数短路**：`Exponent::One` 在 chunk 0 直接加到累加器；`Zero` 直接 `skip`。

### 5.2 每次调用的静态参数（Spend）

| MSM 调用 | 群 | n (标量数) | c | 桶数/chunk = 2^c−1 | chunk 数 = ⌈255/c⌉ | 桶元素类型 |
|---|---|---:|---:|---:|---:|---|
| H query | G1 | 131,071 | 12 | 4,095 | 22 | G1Projective |
| L query | G1 | 98,638 | 12 | 4,095 | 22 | G1Projective |
| A input | G1 | 8 | 3 | 7 | 85 | G1Projective |
| A aux | G1 | 98,638 | 12 | 4,095 | 22 | G1Projective |
| B-G1 input | G1 | 8 | 3 | 7 | 85 | G1Projective |
| B-G1 aux | G1 | 98,638 | 12 | 4,095 | 22 | G1Projective |
| B-G2 input | G2 | 8 | 3 | 7 | 85 | G2Projective |
| B-G2 aux | G2 | 98,638 | 12 | 4,095 | 22 | G2Projective |

例：n = 131,071 → ln = 11.78 → c = 12；桶数 4095；⌈255/12⌉ = 22 chunks。

## 6. 证明大小与验证

### 6.1 为什么是 192 字节

`GROTH_PROOF_SIZE = 48 + 96 + 48 = 192`（`sapling-crypto/src/constants.rs`）：

| 分量 | 群 | 压缩编码 |
|---|---|---:|
| π_A | G1 | 48 B |
| π_B | G2 | 96 B |
| π_C | G1 | 48 B |
| **合计** | | **192 B** |

> Spend 和 Output 的证明大小都是 192 B，与电路规模无关（Groth16 的常数大小证明）。

### 6.2 验证

- 公开输入：Spend **7** 个域元素（rk、value commitment、anchor、nullifier 的打包），Output **5** 个（value commitment、ephemeral pk、note commitment）。
- 验证算法：Groth16 pairing 检查 `e(A,B) = e(α,β)·e(IC,γ)·e(C,δ)`，其中 `IC` 由公开输入与 VK_IC 点组合（Spend VK_IC 有 8 个点，Output 6 个）。多个 Miller loop 可批处理。
- 实测：Spend 2.790 ms、Output 2.150 ms → **验证比证明便宜约 1200×（Spend）/ 240×（Output）**。

### 8.2 单线程 worker fallback（已消融：是计时归属现象，不是瓶颈）

单线程诊断批次中观察到的签名：

- 每次证明都记录到 **worker fallback**（5/5 证明出现）。
- B-G1 aux 调用：`submit_elapsed_ms` 中位数 **2,334.96 ms**，`task_start_delay_ms` 中位数 **2,123.68 ms**，而该调用自身 `elapsed_ms` 中位数仅 **211.22 ms**。
- 对应的 `assignment_query_prep_dispatch_ms` 阶段中位数 **2,428.592 ms**。

20 线程时：无 fallback 记录，B-G1 aux 提交中位数约 0.002 ms，该阶段降到 13.714 ms。

**结论（2026-10-17 受控消融）：** 该签名确实存在，但它是**计时归属**而非额外开销。固定线程数=1、绑核（`-AffinityMask 1`）、ABBA 配对后，A（fallback）与 B（强制 async）端到端 Prove 差 **+1%（+41 ms 均值，U=29，p≈0.11，n=10/条件，不显著）**；强制 async 只是把约 **2.5 s** 从 `assignment_query_prep_dispatch_ms`（2523.8→7.3 ms）挪进 `wait_and_assembly_ms`（634.1→3168.1 ms）。详见 `experiments/metadata/sapling_spend_worker_fallback_ablation_conclusion_20261017.md`。

### 8.3 受控消融实验（已完成）

`experiments/metadata/sapling_spend_worker_fallback_ablation_protocol_20261016.md` 定义了把线程固定为 1、只改 worker 调度分支（`-ForceAsyncWorker`）的 A/B 对照。**已于 2026-10-17 完成（ABBA 配对 + 绑核），结论：fallback 对端到端 Prove 无可测影响，只是计时归属/调度现象。** 数据在 `sapling_spend_prover_runs_fallback_ablation*.csv`，不混入正式基线。

> **方法学告警（重要）：** 本机为混合架构 CPU（i7-14700）。单线程 worker 不被绑定核时，OS 可能把它放到 E-core，导致 Prove **2.1×** 变慢（LP0≈3.8 s vs LP20≈8.1 s，参数加载 25 s vs 54 s）。这解释了 2026-10-16 历史批次“8.5 s vs 3.6 s”的波动。**单线程测量必须绑核，否则结果有 2.1× 不确定性。**

### 9.1 用“操作计数”看为什么 bucket fill 是 MSM 内部重点

- 960 万级 fill 槽位 vs 90 万次 reduce 迭代 vs 90 万次 reduce 群加 → fill 是数量级最大的一环。

### 9.3 内存维度的排序更新（2026-10-18，来自目标 a 的阶段归因）

## 11. 测量口径与局限（必读）

1. **批次不可混用。** 正式基线（Spend `1791613854129`、Output `1791549582046`）、线程扩展批次、插桩 profile 批次、诊断批次口径不同。
2. **插桩有开销。** 重度插桩批次 Prove 可达 8 s，绝对时间不可当正式基线，只能看**相对成本结构**。
3. **并行下 MSM elapsed 会重叠。** 不能把 8 次调用 elapsed 相加当作墙钟或“最大可加速比”；诊断批次里该比例可达 246%（`sapling_spend_profile_run_summary_1792220451370.csv`），正是因为调用并行。
4. **阶段计时是源码区间计时。** 可能包含同步/fallback 工作，不是互斥 CPU 分解。
5. **参数文件大小 ≠ CRS/PK/VK 大小 ≠ 运行时内存 ≠ 证明大小。**
6. **桶内存是静态估算**，不是分配器峰值；账本尚未闭合到 101 MiB。
7. **系统因素未完全受控**（CPU 频率、微信后台、电源策略），部分批次波动未解释。

fill 槽位   = n × chunks

**闭合验证：** 加载后实测 60,818,440 B 与静态 `capacity_payload` 60,819,152 B 仅差 **712 B**；单线程绝对高水位 100.29 MiB 与既有整进程 `PeakWorkingSet64 = 101.30 MiB` 吻合（分配器 live 略低于 WS，合理）——即“101 MiB”就是**参数常驻 + Prove 单峰**，而非两个不同峰叠加。

### 13.2 缺口 1：峰值落点

峰值发生在 **H query 的 G1 MSM 调用内部**：

```
H 调用进入时 live               78,596,989 B   (实测)
+ H 窗口化指数表示              25,970,216 B   (实测)
= 104,567,205 B
+ 1 个 G1 桶数组 (4,095×144)       589,680 B   (实测)
= 105,156,885 B   ≈ 观测峰值 105,160,229 B  (残差 3,344 B)
```

> **口径修正（2026-10-18，见 §21.6）：** 上式里的 25,970,216 B 是**净值**（测点时源 `Vec<Scalar>` 已释放），因此与 §17.2 直接普查的 **26,214,200 B 毛值**相差恰好一个源向量 4,194,304 B。**引用该缓冲时必须写「外层 + 堆」的毛值**：c=12 为 **26,214,200 B**，c=13（有符号默认）为 **24,117,064 B**。目标 a 之前的三个不一致数字（26.2 / 22.0 / 19.9 MB）即由此而来。

### 13.3 缺口 2：桶数组实测（逐一吻合静态估算）

单线程 `BELLMAN_MSM_MEM_PROBE` 显示：G1 4,095 桶 = **589,680 B**、G2 4,095 桶 = **1,179,360 B**、输入 7 桶 = 1,008 / 2,016 B，全部与 `桶数×size_of(projective)` 到字节吻合。桶数组在每个 chunk 闭包内一次性分配、返回即释放。**结论：静态桶估算成立，但桶不是并行内存增量的主因。**

### 13.4 缺口 3：指数转换瞬态

groth16 第 292/309/316 行的 `Vec<Scalar> → Vec<Exponent>`：因 `into_iter` 期间源缓冲仍存活，瞬态 = 源 + 目标。Spend 实测：input 576 B、aux **7,101,936 B**、h **9,437,112 B**；转换后常驻即目标 `Exponent` 向量（aux 3.76 MiB、h 5.00 MiB）。属**有界瞬态**，优先级低。

> **口径精化（2026-10-17 晚，见 §17.1）：** 上表是**受控微测量**的「源 + 目标 = 该窗口的绝对 footprint」。**in-situ 峰值增量**（= 真实流程里 live 的峰值抬升）另有其值：Spend h 为 **5,242,840 B**（＝目标向量本身，源在转换前已计入 live），Spend aux 为 **9,361,800 B**（＞源+目标，因为此时 **h 的 MSM 仍在后台运行**，其工作缓冲落在同一窗口）。**峰值记账请用 in-situ 数**，微测量数只用于说明"源+目标是多少"。

### 13.5 新主因：MSM 的“窗口化指数表示”

`Exponent::chunks(c)` 产出 `ChunkedExponent::Chunks(Vec<u64>)`，**只有非零指数才分配** `chunk_count × 8` B（c=12 → 22×8 = 176 B/项，另有外层 `Vec` 每元素 32 B）。实测单线程窗口化增量：

| 调用 | 指数数 | c | chunk | 增量 | 平均 B/指数 | 推断非零密度 |
|---|---:|---:|---:|---:|---:|---:|
| **H query (G1)** | 131,071 | 12 | 22 | **25,970,216 B (24.77 MiB)** | 198.1 | ~94% |
| L / A_aux (G1) | 98,638 | 12 | 22 | 7,397,608 B | 75.0 | ~24% |
| B_aux (G2) | 98,638 | 12 | 22 | 7,396,664 B | 75.0 | ~24% |
| A/B input | 8 | 3 | 85 | 4,360 B | 545 | — |

**这是 Spend Prove 最大的单笔瞬态（~26 MB）**，远大于桶数组（0.59 MB）与指数转换（≤9 MB）；它同时是并行峰值抬升（100→135 MiB）的主因：多线程下不同 MSM 调用的窗口化缓冲同时驻留。

> **口径（2026-10-18 冻结，见 §21.6）：** 上表「增量」列是**净值**（源 `Vec<Scalar>` 已释放）。该缓冲的**毛值口径**为「外层 24 B/指数 + 堆 8 B/槽」：c=12 = 3,145,704 + 23,068,496 = **26,214,200 B**；有符号 c=13（当前默认）= 3,145,704 + 20,971,360 = **24,117,064 B**。二者与实测净值的差恒为 4,194,304 B（±4,696 B 分配器残差），闭合。**引用一律用毛值。**

> **⚠️ 上表「推断非零密度」一列已被 §17.2 的直接普查纠正，请勿再引用该列。**
> 直接普查（`multiexp.rs` 加可关闭的计数插桩）结果：
>
> | 调用 | `Zero` 指数 | `One` 指数 | `Chunks` 指数 | `Chunks` 内槽非零率 |
> |---|---:|---:|---:|---:|
> | H query (G1) | 0 | 0 | 131,071 (**100%**) | **99.35%** |
> | L / A_aux / B_aux | 37,409 (37.9%) | 32,648 (33.1%) | 28,581 (29.0%) | **99.37%** |
>
> 即：**H 实际上是满密度（~99.35%），之前的 ~94% 是字节模型产物**（模型错误地假设外层 32 B/元素且始终存满 22 槽；实测 `ChunkedExponent` = 24 B，模型闭合验证见 §17.2）。**L/A/B 的"低密度"不是零 chunk，而是 71% 的指数恰好等于 0 或 1（零堆分配）**。
> 结论不变（窗口化表示仍是最大单笔瞬态），但**优化含义变了**：H 只有 0.65% 的槽是零，**无法靠"跳过零 chunk"省内存**，只能靠"不物化/换表示/减小 `c`"。

### 13.6 对瓶颈排序的更新

- **排名 #1（MSM）在内存维度上要改口径：** 主因是 **H query 的窗口化指数缓冲**，而不是桶数组。新的优化方向 = 降低窗口化表示成本（减少窗口数 `c`、按需生成窗口、位切片/就地表示）。**注意（§17.2）：H 的槽非零率高达 99.35%，所以"跳过零 chunk"这条路基本无效**；而 L/A/B 的 71% 指数本来是 0 或 1，已被短路、无堆分配。
- **新增权衡项：** 并行化把 Prove 瞬时内存从 ~34.5 MB 抬到 ~68.8 MB（1→8 线程），内存敏感部署需权衡。
- 指数转换（≤9 MB 瞬态）与桶数组（0.59 MB/个）**不是**当前内存瓶颈。

### 15.2 核态参照：为什么必须绑核

同 exe、同 1 线程，只改亲和性：

| 掩码 | 含义 | Spend pooled 中位 | Output pooled 中位 |
|---|---|---:|---:|
| `0x1` | 单个 P-core | 3711.5 ms | 558.7 ms |
| `0xFFFF` | 全部 16 P 逻辑核 | 3842.2 ms（+3.5%） | — |
| `0xFFF0000` | 仅 12 E-core | 7803.6 ms（**2.10×**） | 1206.4 ms（**2.16×**） |

- 连"绑到全部 P 核"都比"绑到单核"慢 3.5% ⇒ 单线程基线应绑**单个逻辑核**。

### 15.3 绑核线程扩展与非单调性的判定

掩码固定 `0xFFFF`（16 个 P 逻辑核），2 批/配置：

| 线程 | 中位 (ms) | 批内极差 | 加速 | 并行效率 | 相对上一档 |
|---:|---:|---:|---:|---:|---:|
| 1 | 3842.248 | 4.80% | 1.000× | 100.0% | — |
| 2 | 1890.879 | 5.58% | 2.032× | 101.6% | 2.03× |
| 4 | 1064.321 | 5.90% | 3.610× | 90.3% | 1.78× |
| 8 | 816.862 | **17.37%** | 4.704× | 58.8% | 1.30× |
| 16 | 785.935 | **22.21%** | 4.889× | 30.6% | 1.039× |
| 20 | 808.368 | 11.29% | 4.753× | 23.8% | **0.972×（变慢）** |

**判定（原来列为"未闭合"）：**
1. 4→8 只有 1.30×、8→16 只有 1.039× ⇒ **8 线程起已经饱和**，瓶颈不是线程数（而是内存带宽/桶合并的串行尾段）。
2. 16→20 **变慢 2.9%**：20 > 16 个 P 逻辑核，多出的线程与既有线程争抢物理核（HT 竞争），而 `bellman` 的 `WORKER_SPAWN_MAX_COUNT = 4×current_num_threads()` 还会随线程数放大任务队列 ⇒ **只有额外开销，没有额外并行度**。
3. 方差在 8/16 线程最大（17%/22%），20 线程反而降到 11%，与"16 线程正处在饱和拐点、抖动被放大"一致。
⇒ **非单调性 = 饱和 + 过订阅，不是算法/调度缺陷。** 可执行方向是"把线程钉在 4–8"和"缩短串行尾段"，不是继续加线程。

**对 §13.5 的纠正（重要）**

| 项 | 旧（字节反推） | 新（直接普查） |
|---|---|---|
| H 槽非零率 | ~94% | **99.35%**（100% 为 `Chunks`）⇒ 实为满密度 |
| L/A/B "密度" | ~24% | `Chunks` 内 **99.37%**；但只有 **29.0%** 的指数是 `Chunks`，其余 **71% 恰为 0 或 1**（零堆分配） |

**优化含义：**
- **H 的 ~26 MB 无法靠"跳过零 chunk"缩小**（仅 0.65% 槽为零）；只能 **(a) 不物化（按需/分块惰性展开）、(b) bit-slice/signed-digit 表示、(c) 减小 `c`**（槽数 ∝ ⌈255/c⌉，但桶数 ∝ 2^c，需权衡时间）。
- **L / A_aux / B_aux 的 0/1 短路本来就有效**，针对它们的省内存改动收益上限有限。
- ⇒ **内存优化目标应聚焦 H query**，与 §13 的峰值归属一致。

> **后续（2026-10-18，见 §21）：** 方向 (a)「不物化」已实现并完成预注册验收——只预存进位位（1 bit/窗口/指数）、窗口数字在 fill 时即时折叠。实测该缓冲 **24,117,064 → 327,680 B**，现场瞬态 −23,789,344 B，端到端 1t −4.60%；但 prove 峰值只降 12.93 MB（<15 MB 阈值）而**未通过**，原因是一个与窗口化表示无关的 **90.13 MB 独立天花板**（`qap_fft_h_exponent_prep` 阶段）。方向 (c)「减小 `c`」经核算为净亏（桶数 ∝ 2^c 增长快于槽数缩减，见预注册 §2.3）。

1. **【稳健，建议采纳】** 把证明进程亲和性限制到 **P 核集合**：消除读取阶段落到 E 核的风险，Spend 单进程省约 **25 s**（该阶段 1.8–1.9×），prove 阶段无实测退化。对 Output 中性（其读取阶段仅 1.8 s）。

## 20. 优化目标 b：H query G1 MSM 的有符号窗口重编码（2026-10-17 完成）

> 预注册（冻结于 `c507e0e`）：`experiments/metadata/sapling_msm_signed_digit_preregistration_20261017.md`；
> 结果元数据：`experiments/metadata/sapling_msm_signed_digit_results_20261017.md`。
> 本节阈值与判据全部引用上述冻结文件，未事后修改。

### 20.1 机制：把无符号窗口换成平衡有符号窗口

§5 把 Spend 的时间主因定位到 MSM，§13/§17 的实测又把 MSM 内部的成本压到 `bucket_fill`。本次改变的是**指数窗口的数字表示**：从"无符号 `c` bit"换成**平衡有符号（balanced / BOS–Coster 型）数字**。

- 数字取值 `d ∈ [−2^(c−1), 2^(c−1)]`，以 `+2^(c−1)` 偏移存储，桶下标恒为 `|d| − 1`；
- 同一窗口宽度下**桶数减半**（`2^(c−1)` vs `2^c − 1`），省下的预算换来**多 1 bit/窗口**；
- n = 131,071（H query）时：**22 个 12-bit 窗口 → 20 个 13-bit 窗口**，桶数组 4095 → 4096（几乎不变），总群加次数 3,063,742 → **2,785,260（−9.1%）**。

这是"算法级"而非配置级：它改变指数的数字表示与桶数组大小，从而改变根号下的群加**次数**。

### 20.2 为什么选它（动手前实测排除了其它三类候选）

| 候选 | 实测 | 结论 |
|---|---|---|
| 桶数组变小（访存假设） | `add_rand_bucket` 在 36 KB / 147 KB / 590 KB 桶数组下 = 468 / 467 / 478 ns | 单次群加**与桶数组大小无关** ⇒ 不是访存受限 |
| 构建开关（LTO / `target-cpu=native`） | 默认 470 ns；`native` 455；`lto=fat`+`cgu=1` 465；两者 441 | 最好 **−2.7%**（噪声量级）⇒ 排除 |
| 纯窗口调参（不改编码） | 无符号 c=13 群加 −3.7% | 空间太小 |
| **有符号窗口 c=13** | 群加 **−9.1%** | **采用** |
| wNAF | 需 131,071 × 2^(w−1) 个预计算点 | 内存不可接受（预注册 §7） |

单次混合加 470 ns ≈ 11 次 `Fp` 乘 × 43 ns，与 bls12_381 的 RCB2015 Alg.8 吻合 ⇒ **算术受限**，因此"减少群加次数"是唯一有效杠杆。

### 20.3 实现中抓到的一个真实进位 bug

平衡重编码的每个窗口都可能向上一窗口进位。**当 `c` 整除 255（c = 3/5/15/17/51/85）时，最高窗口是满宽度的，末位进位非零**，因此窗口数必须是 `255 / c + 1`（整除下取整 +1），而不是 `ceil(255/c)`；否则最上位进位被静默丢弃、结果错误。c = 12/13（本次默认）恰好不是 255 的因子，所以该 bug 只在扫描其它宽度时暴露——微基准的 **2..=20 全宽度扫描**加上 debug 构建的 `debug_assert`（末位进位必须为 0、被截断窗口必须全为零）把它挡住了。

### 20.4 正确性（四项全过）

| 项 | 结果 |
|---|---|
| ① 真实证明 | 主/辅/内存各批 **78/78 `verified=true`、`proof_bytes=192`** |
| ② 两种编码逐位相同 | 微基准在窗口宽度 **2..=20 每个宽度**下断言有符号与无符号的 MSM 结果（n = 131,071 整规模） |
| ③ 朴素对照 | 64 项前缀 == double-and-add（两种编码，c = 1/3/5/8）；n = 8 小查询路径 |
| ④ 参数与电路规模不变 | spend `8e48ffd2…`、output `2f0ebbcb…`；约束规模未改 |

### 20.5 主指标：Spend 1t @ `0x1`（冻结阈值 ≥3%）

同一二进制（spend `e498c605…`），A = `SAPLING_MSM_SIGNED_DIGITS=0`、B = `=1`，**ABBA / ABBA / BAAB** 三轮交错（末轮反转顺序），各 6 批 × 5 次证明：

| 口径 | A（无符号） | B（有符号） | 变化 |
|---|---:|---:|---:|
| 批中位 pooled | 3903.6 ms | 3644.9 ms | **−6.63%** |
| 单次证明 pooled 中位 | 3887.9 ms | 3652.6 ms | **−6.05%**（MWU **p < 1e-4**） |

## 21. 优化目标 a：H query 窗口化表示「去物化」（2026-10-18 完成）

预注册（冻结，先于代码改动）：`experiments/metadata/sapling_msm_lazy_recoding_preregistration_20261018.md`（提交 `85ffb0d`）。
结果全文：`experiments/metadata/sapling_msm_lazy_recoding_results_20261018.md`。

### 21.1 机制与为什么

`multiexp_inner` 的并行轴是**窗口**（`(0..window_count).into_par_iter()`），窗口乱序并发，因此"按窗口顺序滚动推进进位"不可行——这是被侦察推翻的第一版设计。采用的机制是：**只预计算有符号重编码的进位位**（1 bit/窗口/指数），窗口数字在 fill 循环里由「源位段 + 该窗口进位位」即时折叠。

- 进位位图：n × 20 bit = **327,680 B**（原来 24,117,064 B）；
- 位段随机访问 O(1)：`bls12_381::Scalar::ReprBits = [u64; 4]` ⇒ `FieldBits` 是字对齐 `BitArray`，`BitField::load_le` 只走 live head/body/tail 字（`.chunks(c).nth(j)` 会是 O(j)，总计 O(w²) ≈ +10× 提取工作）；
- 与物料化的偏置槽语义**逐位等价**（共用 `signed_slot`），0/1 短路不变；
- 开关 `SAPLING_MSM_LAZY_RECODING`（`0` = 物料化，`1` = 进位位），**默认保持 `0`**。

### 21.2 正确性（全过）

| n=8 小查询路径（c=3） | 4/4 |
| 跨重编码一致性、内建窗口规则与显式扫描一致 | 6 + 7 |
| 全部 120 次证明 `verified=true` / `proof_bytes=192`；参数哈希不变 | 全过 |

### 21.7 判定与建议

**判定：未通过（主指标 12.93 MB < 15 MB）⇒ 按预注册回退条款记为「局部改动未转化为峰值下降」，归档，开关默认保持 `0`。**

同时产出三项可继续使用的资产：

1. **可复用的峰值归因探针** `SAPLING_G16_MEM_PHASE_PROBE`（默认关闭），把 prove 峰值从一个数字变成一张按阶段的表。
2. **内存主因已更新**：新的主因**不是** H query 窗口化缓冲，而是 **`qap_fft_h_exponent_prep` 阶段（QAP/FFT 域向量 + H 指数转换）的 90.13 MB 绝对峰值**——它等于进入该阶段的 live（85.94 MB）加一个域大小的缓冲（4.19 MB），相对阶段结束时的 live 则高 11.53 MB，且与重编码开关完全无关。这是下一步内存优化的自然目标（`h_exponents` 的现场转换瞬态、三个域向量 `a/b/c` 的同时驻留）。
3. **一个已验证更快的改动**（三个臂集全部更快，峰值 −12.93 MB，正确性全过）。

**方法论教训（应写入后续内存目标的立项规范）：** 预注册的 15 MB 阈值建立在「峰值 ≈ 该缓冲 + 其它」的单点模型上，**未先做阶段分解**。正确做法是先用阶段探针测出「次高阶段」高度 `H2`，把阈值设在 `min(缓冲毛值, 峰值 − H2)` 量级；本例 `H2 = 90.13 MB`，可转化上限从一开始就只有 12.93 MB，15 MB 物理上不可达。

**是否把默认值改为 `1` 属所有者决策，冻结判据不授权**（规则在不知存在 90.13 MB 天花板的情况下设定）：保持 `0` 则归档为已验证候选，待天花板一并处理后以组合收益重新立项；改为 `1` 则需显式记录「该默认值变更不由冻结判据授权」。

**所有者决定（2026-10-18）：保持默认 `0`；把 QAP/FFT 阶段天花板（90.13 MB）立为下一优化目标。** 组合关系必须写进下一目标的预注册：在当前默认（lazy=0）下全局峰值由 H query 窗口化缓冲所在区间决定，**单独压低 QAP/FFT 阶段峰值不会改变 shipped default 的全局峰值**（会再次出现「阶段降了、峰值没动」）。因此下一目标的主指标应预注册为「**`SAPLING_MSM_LAZY_RECODING=1` 配置下**的 prove 峰值下降」，并在天花板落地后以「lazy=1 + 天花板下降」的组合重新立项，届时默认值切换才被显式授权。

## 22. 优化目标 f：单线程 FFT four-step scratch 消除（2026-10-18 完成）

### 22.1 机制与为什么

## 23. 优化目标 g：组合验收与默认值切换（2026-10-18 完成）

目标 a 与目标 f 各自归档/通过后，两个开关的收益被阈值切开：a 单独 12.93 MB 够不到 15 MB，f 只降 `lazy=1` 配置的天花板。目标 g 把 **`lazy=1` + FFT scratch 消除作为一个组合**正式验收，并作为默认值切换的唯一授权路径。预注册（`sapling_combo_default_preregistration_20261018.md`，`9e7ee2e`）先于任何测量冻结：主指标 = 当前默认臂 (lazy=0, fix=0) → 拟新默认臂 (lazy=1, fix=1) 的 prove 峰值中位下降 ≥ 15,000,000 B（继承目标 a 的门槛，不随预期上调）；辅项 = 正确性、三臂集时间非退化（≤ +1%）、翻转后复验。

### 23.1 判定：通过（六项全过），默认值已切换

| 指标 | 冻结阈值 | 实测 | 判定 |
|---|---|---:|:--:|
| **主**：组合 prove 峰值下降 | ≥ 15,000,000 B | **−16,878,888 B（−16.38%）**：103,063,495 → 86,184,607 B | **MET** |
| 辅 1：正确性 | 100% | 台账 10/10 + 时间战役 360/360 + 翻转后 5/5 | **PASS** |
| 辅 2：时间非退化（三臂集） | 每臂 ≤ +1% | spend 1t −5.81% / spend 8t −3.95% / output 1t −2.35%（均为负） | **PASS** |
| 辅 3：切换后复验 | 三项全过 | 门禁 12/12 一致；台账 +7 B；批次 5/5 | **PASS** |

- 主指标超门槛 1.88 MB；两臂 `live_before_prove` 逐位相同（68,729,865 B），差异全在 prove 阶段内部。重测值与目标 f 归档值偏差 ≤ 239 B（分配器粒度），互相印证。
- 时间三臂全部更快且配对 5/5、敏感性 6/6（p=0.0312）；但按预注册范围，时间只作附证（output −2.35% 低于协议 §4 的 3% bar，单独不可分辨）。
- **辅 3 落地**（`d4ed1df`）：`SAPLING_MSM_LAZY_RECODING` 与 `SAPLING_FFT_SERIAL_SINGLE_THREAD` 默认值 0 → 1，重编译后不设任何开关：门禁 digest 与显式四步法逐位一致（12/12）、台账峰值 86,184,614 B（+7 B）、批次 5/5 验证——翻转后的默认行为与验收臂逐字节等价。

### 23.2 结论

1. **【通过并切换】** shipped default 的 prove 峰值 **103.06 → 86.18 MB（−16.4%）**；单线程端到端同会话对照 −5.81%（附证）。这是本工程第一个把默认值真正切换掉的优化组合。
2. **【候选清单】** 协议 §7 候选：a（未通过归档）、b/e/f/g 均已完成；c（B-G2 aux）与 d（赋值转换并行化，预期 <3%）未做。
3. **【下一内存目标】** 翻转后的 86.18 MB 峰值由 `circuit_synthesis` 阶段决定（§22 已测），下一目标必须先做阶段分解再立阈值，避免重犯目标 a 的阈值错误。

## 24. 优化战役完结：两条线均到达地板（2026-10-18）

目标 g 切换默认值后，按既定方法论（先阶段分解、再立阈值）对新的 shipped default
做了两个维度的结项侦察。结论：**内存线与时间线均到达各自地板，战役 a–g 完结，
不再设立新目标。**

### 24.1 内存线：结构性地板（86.18 MB）

侦察文档 `sapling_default_stage_decomposition_20261018.md`，数据：阶段探针 +
新增合成容量探针（`SAPLING_G16_SYNTH_CAPACITY_PROBE`），5 次运行跨运行确定。

- 全局峰值 86,184,603 B 归属 `circuit_synthesis` 末端；第二高阶段峰值为
  `assignment_query_prep_dispatch` 的 82,870,091 B ⇒ 物理可转化上限 **3,314,512 B**。
- 峰值构成：60.8 MB 参数（证明期全程在役）+ 7.9 MB 见证准备（必需）+
  16.78 MB 赋值向量容量 + 0.25 MB 合成瞬态。
- 容量实测：a/b/c/aux 的 capacity 均为 131,072 = QAP 域大小——**不是余量**，
  被 `from_coeffs` 的 `resize` 原地填零后整体移入域；若预留下精确长度，
  重分配瞬态会落进 QAP 阶段并把峰值抬到 ≈87.0 MB。唯一真余量是 aux 的
  1,037,888 B，峰值点不可释放（`shrink_to_fit` 瞬态 +3.16 MB；预知见证数无干净机制）。
- 即使假设全部真余量可去，峰值也只落到 ≈85.14 MB。⇒ 上限 3,314,512 B **不可达**。

### 24.2 时间线：算术地板（1 线程 prove ≈3.4 s）

侦察文档 `sapling_default_time_profile_20261018.md`，数据：阶段墙时间 + MSM
阶段剖面（剖析开销只用于取比例）。

- 阶段墙时间（中位）：合成 120.5 ms（3.3%）、FFT+h 转换 385.8 ms（10.6%）、
  MSM 队列排空 3,100 ms（85.4%）。
- MSM 按 query：H query 1,514 ms（fill 93.5%）、G1 aux 987 ms、B-G2 aux 635 ms
  （reduce 44%）、IC 可忽略；fill 合计占 MSM 78%。
- fill 每非零数字 462 ns（同批次实测：H query 2,620,825 个非零窗口数字/证明、
  fill 中位 1,211.7 ms），与源码注释记录的 ~470 ns 混合加一致 ⇒ 算术受限；
  操作数 `windows × (n + 2×buckets)` 由算法固定，操作数模型核算 **c=13 对三大
  query 均已最优**（H：c=12 +6.8%、c=14 +0.6%；G2 aux：c=12 +0.7%、c=14 +11%）。
- 候选 c 无机制（fill 同循环、reduce 倍加固定、调窗无净获益）；候选 d 低于 bar
  （赋值转换占 prove <1%）。`wait_and_assembly` 的 640.8 ms 经追溯是 worker
  队列尾部而非装配算术。

### 24.3 陈述边界

- 两条结项都只覆盖**本管线**（vendored bellman + Sapling Spend/Output + 既定开关体系）
  与**既定测量口径**（1 线程主守门、8 线程守门）。更换承诺方案、电路重构或
  多线程调度重构不在本陈述范围内。
- 战役产物（目标 b/e/f/g 的收益与默认值切换）不受结项影响，继续有效。
- 后续工程价值在测量与复现性的维护；若未来引入新机制（如按 query 选窗、
  不同的桶元素布局、新的 recoding），应先以本文 §24.1/§24.2 的口径做同款侦察
  再决定是否立项。

## 25. 交易级测量：完整 Sapling 交易构造（2026-10-22）

§1–§24 的时间都是**证明函数**的墙钟（`SpendParameters::create_proof` /
`OutputParameters::create_proof`）。本章补齐此前未覆盖的一层：**真实交易构造器**
`zcash_primitives::transaction::builder::Builder::build(...)` 的端到端本地构造时间。
这是**测量 baseline**，不设立优化目标、不产生收益结论。

**场景（预注册冻结）：** 1 个 Sapling spend（100,000,000 zats）+ 1 个收款 output
（60,000,000）+ 1 个找零 output（39,990,000），ZIP-317 手续费 10,000，`target_height =
1,700,000` ⇒ v5 / `Nu5`；32 层合成 Merkle 路径、固定 zip32 种子；参数文件与既有批次
相同（spend `8e48ffd2…`、output `2f0ebbcb…`）。三个独立进程臂各 6 run，丢弃 run 1，
亲和性设置后读回核验。

| 指标（暖态中位） | A1 真实 1t @ `0x1` | A2 真实 8t @ `0xFFFF` | A3 mock 1t @ `0x1` |
|---|---:|---:|---:|
| **`t_total_construct` = build + serialize** | **4,292.720 ms** | **1,176.072 ms** | 4.888 ms（对照） |
| `t_build` | 4,292.699 ms | 1,176.049 ms | 4.832 ms |
| `t_serialize` | 0.022 ms | 0.024 ms | 0.020 ms |
| `t_proving`（配对 `build − mock_build`） | 4,287.528 ms（**99.88%**） | — | — |
| `sum_proofs`（三份证明之和） | 4,292.703 ms | 1,175.588 ms | 4.367 ms |
| Spend / Output A / Output B | 3,321.5 / 480.2 / 486.2 ms | 928.0 / 132.7 / 127.9 ms | mock |
| `t_verify`（不计入构造） | 10.384 ms | 13.826 ms | 未做 |

**结论：**

1. **构造时间 = 证明时间。** 99.88% 的 `t_build` 是 Groth16；sighash、Spend 授权签名、
   binding 签名、bundle 装配与序列化合计约 **5 ms（0.11%）**。这说明 §24.2 的算术地板
   直接决定交易构造速度：证明耗时压到地板，交易构造就压到地板。
2. **两个独立估计在 0.12% 内闭合**（配对 `t_proving` 与 `sum_proofs`，`t_build` 的
   0.121%），因此"证明占 99.88%"不是单一估计量的假象。
3. **8 线程把总构造时间压到 1/3.65（并行效率 45.6%）**，Spend 与 Output 的加速比分别
   为 3.58× / 3.62–3.80×，与既有"8 线程饱和"结论一致。
4. **交易形状决定边际成本。** 1t 下每多一个 Spend 约 +3.3 s，每多一个 Output 约
   +0.48 s；序列化可忽略，验证约 10 ms。这是"把单项证明耗时相加"在本形状下恰好近似
   成立的原因（4,287.9 + 5 ≈ 4,292.7 ms），但换形状后不成立。

**验收：** 冻结表 7/7 通过（主判据 18/18：12 条真实交易全部 `BatchValidator` 通过，
6 条 mock 结构通过；结构常量 2,377 B / V5 / 1 spend / 2 outputs / fee 10,000 /
balance +10,000 全同；证明占比 0.9988 ≥ 0.90；双估计差 0.121% ≤ 5%；非证明开销
4.832 ms ≤ 100 ms；A1 CV 0.668% ≤ 5%；序列化残差 0.001 ms）。

**边界：** 本地构造时间，**不含**参数加载（约 27 s，已置于计时窗口外）、钱包输入选择、
手续费迭代、note 解密、数据库 IO、广播、mempool、打包与确认；Merkle 路径/Note 为
**合成测试状态**，不代表真实钱包 note。测量前发现并留痕的手续费口径偏差
（15,000 → 10,000；`value_balance` −15,000 → +10,000）见预注册 §10。

`experiments/raw/csv/sapling_tx_construct_runs_{real,mock}.csv`；派生表
`results/tables/sapling_tx_construct_{summary,composition,acceptance}_20261022.csv`；
