# 范围界定：本地真实输入交易构造与证明基准（相对「完整交易耗时」）— 2026-10-26

> 本文件界定一项**计划中的**基准工作的范围与边界，不报告任何测量结果。
> 它把结项报告（[`../../docs/msm_kernel_project_closeout_20261023.md`](../../docs/msm_kernel_project_closeout_20261023.md) §5.3）中的「换物理主机的真实证明复现」与既有本地交易构造实验
> （`sapling_tx_construction_*{preregistration,results}_20261022.md`）统一到一个更精确的定位下，
> 并明确把「完整交易生命周期」作为**单独的后续网络阶段**，不混入本工作。

---

## 0. 一句话定位

这项工作是一项**本地**基准：**真实 Note / witness 接入 → 交易构造 → 证明生成 → 序列化 → 本地验证**。
它回答「在本地计算链路上，一笔真实输入的交易构造与证明要多久、瓶颈在哪」，
**不是**「用户从点击发送到交易确认要多久」。后者是端到端用户体验耗时，需要单独的网络阶段才能回答。

---

## 1. 工作边界

### 1.1 覆盖（本地计算链路）

| 环节 | 说明 |
|---|---|
| 真实 Note / witness 接入 | 从真实链上状态 / 钱包导出的 note、Merkle 路径与 anchor，而非合成 Merkle 状态 |
| 交易构造 | 真实 `zcash_primitives::transaction::builder::Builder::build(...)`，含 Sapling 证明、sighash、Spend 授权签名、binding 签名、bundle 装配 |
| 证明生成 | Groth16 证明（走本工程插桩版 bellman） |
| 序列化 | 交易对象 → 字节 |
| 本地验证 | 构造后交易的密码学校验（结构常量 + 证明/签名/binding sig 全验） |

### 1.2 不覆盖（明确不是本工作的目标）

- **不测网络**：不广播、不连节点、不等确认；本工作的任何计时都不是「到账时间」。
- **不测钱包运行时**：不实现输入选择、手续费迭代、note 解密、数据库 IO、状态机。
- **不回答端到端用户体验耗时**：用户从点击发送到交易确认的总时间，需要广播、mempool、打包、确认与钱包同步扫描——这些都不在本工作内（见 §4）。

---

## 2. 它能回答 / 不能回答

- **能回答**：
  - 真实链上状态（真实 note / witness）是否会改变既有性能结论。既有 `sapling_tx_construction`（2026-10-22）用的是**合成 Merkle 状态**，二者在校验 / witness 计算成本上可能同阶但不同；本工作用真实输入补齐这一外部有效性缺口。
  - 作为钱包 / 交易构造器的**本地工程基线**：构造与证明的本地成本、证明占比、序列化与本地校验成本。
- **不能回答**：用户从点击发送到交易确认需要多久。该问题属于完整交易生命周期，见 §4。

---

## 3. 与既有 2026-10-22 本地交易构造实验的关系

- 既有实验（`sapling_tx_construction_preregistration_20261022.md` / `sapling_tx_construction_results_20261022.md`）已经把真实 `Builder::build` 链路本地跑通并分段计时：
  - 1 线程 `t_total_construct` 中位 **4,292.7 ms**，证明占比 **99.89%**，非证明开销 **4.83 ms**，本地验证 **10.4 ms**；
  - 该实验**仅使用合成 Merkle / witness 状态**（`INDEX.md` 行已标注 "synthetic Merkle state"）。
- 本工作（真实输入版本）是在同一本地代码链路之上，**把合成状态替换为真实链上 note / witness**，其余链路不动。
- 因此「当前计划做完」= 一次完整的**本地**交易构造与证明实验（真实输入升级版）；它**不算**完整的链上交易生命周期。

---

## 4. 若扩展到完整交易生命周期：单独网络阶段，分开报告

如果后续要回答完整交易过程，应在本工作之后**单独增加一个网络阶段**，并且把网络指标与本地指标**分开报告**，不要混在一个「总耗时」里——否则无法判断瓶颈来自证明、网络还是确认等待。

| 指标 | 定义 | 计量起点 → 终点 |
|---|---|---|
| `broadcast_accept_ms` | 广播到 Testnet 节点并被接受的时间 | 发送交易字节 → 节点返回 accepted |
| `mempool_wait_ms` | 进入 mempool 到被打包的时间 | 进入 mempool → 落入区块 |
| `confirmation_ms` | 打包后到 N 个确认的时间 | 区块高度 +1 → 达到 N 确认 |
| `wallet_sync_scan_ms` | 钱包同步、扫描和 Note 发现时间（必要时单独测） | 钱包启动 / 新块到达 → 发现并解码相关 note |

- 这些指标**不应和 `Builder::build` / Groth16 prove 时间混在一个「总耗时」里**。
- 报告时本地链路（§1.1）与网络阶段（本 §）应各自成表，瓶颈归因才能落到具体环节。
- 网络阶段是否开展，取决于本工作（本地层）的结果是否值得继续投入——先把本地这一层做扎实。

---

## 5. 最终结论

- 本工作定位为**本地真实输入交易构造与证明基准**，不是「完整交易耗时」。
- 它的时间数据对**证明性能**与**外部有效性**有参考价值（可作为钱包 / 交易构造器的本地工程基线），但对**端到端用户体验耗时没有直接代表性**。
- 当前计划（含真实输入升级）做完，算一次完整的「本地交易构造与证明」实验，但**不算**完整的链上交易生命周期。
- 建议：先把这一层做扎实，再根据结果决定是否值得扩展广播与确认实验。
