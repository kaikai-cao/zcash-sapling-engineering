# 范围界定：端到端 Testnet 真实 Sapling 转账——耗时与内存剖析（含本地证明生成分段）— 2026-10-26 修订

> 本文件界定一项**下一阶段**研究工作的范围与边界，不报告任何测量结果。
> 它取代 2026-10-26 初版「本地真实输入交易构造与证明基准」的范围定位：
> 研究目标现已明确为**端到端 Testnet 交易流程**的耗时与内存剖析，本地证明生成的分段计时
> 作为其中关键的子段保留，而非把「完成本地构造」等同于「完成交易流程研究」。
> 既有 2026-10-22 本地交易构造实验（合成 Merkle 状态）与本次范围共同构成对照基线。

---

## 0. 一句话定位

在 Testnet 上完成一笔真实 Sapling 转账，记录钱包从**准备输入到交易确认**的
**全过程耗时与内存**，并尽可能分离**证明生成**的成本。它回答的是
「真实交易从输入准备到确认需要多久、资源峰值在哪里、Groth16 证明占整个流程的多少」，
而不是只回答「本地构造与证明要多久」。

---

## 1. 工作边界

### 1.1 覆盖（端到端全链路）

| 阶段 | 环节 | 记录重点 |
|---|---|---|
| 0 准备 | 钱包与资金准备：同步、准备可花费的真实 Note | 首次同步峰值（一次性成本，单独报告）、可花费 note 就绪 |
| 1 选输入 | 选择输入并准备 witness | 输入选择、链上状态查询等耗时 |
| 2 构造+证明 | 交易构造并生成证明 | **重点记录 Spend / Output proving 分段** |
| 3 签名组装 | 签名、组装与序列化 | 本地构造、最终交易大小 |
| 4 广播确认 | 广播并等待确认 | 节点接受 / 进入区块 / 确认 分别计时 |
| 5 复核 | 收款与资源开销复核 | 验证交易结果，整理各进程峰值内存 |

### 1.2 与「纯本地构造」的关系（关键）

- 2026-10-22 的 `sapling_tx_construction_*` 已把真实 `Builder::build` 链路本地跑通并分段计时
  （1t `t_total_construct` 中位 **4,292.7 ms**、证明占比 **99.89%**、本地验证 **10.4 ms**），但**仅用合成 Merkle / witness 状态**，
  且**不覆盖网络与确认**。
- 本工作把该本地链路作为端到端全链路中的**一段**：在真实链上 note / witness 之上，额外覆盖
  输入选择 / 状态查询、广播、mempool、打包、确认与钱包识别。
- **本地证明生成的分段计时被保留为归因锚点**：即使最后得到「整笔交易花了多少秒」，
  也必须能解释时间消耗在证明、网络还是确认等待——否则黑盒总时间没有解释力。

### 1.3 明确不是本工作的目标 / 边界

- **不把一次性成本混入每笔发送成本**：初次同步、测试资金准备属于一次性，单独报告。
- **不直接假设 Regtest 为可用完整环境**：Zallet 仍 Beta，公开 issue 记录 Regtest 资金到账后
  缺少受支持的完整花费路径（见 §2）。功能验证优先在 Testnet 进行。
- **不立即改写证明器**：本阶段是测量与剖析，不是优化实现；既有 MSM A–C 优化与源码剖析保留为对照基线。

## 2. 技术路线修正（关键）

前期方案依赖旧版 `zcashd` 作为完整交易实验节点，需要修正：

- **zcashd 已结束支持**：官方于 **2026 年 7 月**结束 `zcashd` 支持，且**不支持 NU6.3**；
  当前生态对应方案为 **Zebra 节点 + Zallet 钱包**。
- **Zallet 提供分阶段 RPC**：`pczt_create`（选输入、计算找零）、`pczt_prove`（生成零知识证明）、
  `pczt_sign`（签名）、`pczt_extract`（提取并检查最终交易）。这提供了**逐步记录各阶段**的可能，
  而不是只能拿到一个黑盒总时间——这正是分离证明成本所需的接口。
- **Regtest 谨慎对待**：当前 Zallet 仍处于 Beta，公开 issue 还记录着 Regtest 中资金到账后
  缺少受支持的完整花费路径。因此倾向**先评估 Zebra + Zallet 的 Testnet 流程，先做一笔功能验证，
  再开展重复测量**，而不是马上改写现有证明器。

---

## 3. 实施流程（0–5 步）

0. **准备钱包与资金**：同步、准备可花费的真实 Note。
1. **选择输入并准备 witness**：记录输入选择、链上状态查询等耗时。
2. **构造交易并生成证明**：重点记录 Spend / Output proving。
3. **签名、组装与序列化**：记录本地构造和最终交易大小。
4. **广播并等待确认**：分别记录节点接受、进入区块和确认。
5. **复核收款与资源开销**：验证交易结果，整理各进程峰值内存。

关键原则：既测**真正的发送到确认**，也**保留本地证明生成的分段计时**。

---

## 4. 测量方案

### 4.1 耗时分段（至少分别记录）

钱包与输入准备 · 交易构造 · 各份证明生成（Spend / Output）· 序列化 · 本地验证 ·
广播到节点接受 · 等待首次确认 · 交易最终被钱包识别。

- **确认等待受网络影响，必须与本地证明时间分开报告**，否则无法判断瓶颈来源。

### 4.2 内存分段

分别测量**钱包进程**、**节点进程**，以及**两者同时运行**时的总资源占用；
至少记录峰值工作集与私有内存；**钱包首次同步的峰值、证明生成期间的峰值要独立保留**。
Zallet 官方明确提示：历史扫描的批量大小会显著影响内存占用——记录扫描 batch size。

### 4.3 一次性成本单独报告

初次同步、测试资金准备属于一次性成本，单独成表，不与每次发送交易的成本混算。

### 4.4 重复与统计

第一笔跑通后，再用**多笔不同的可花费 Note** 重复测试，报告中位数与波动范围；
确认等待时间受网络影响，与本地证明时间分开。

### 4.5 基线对照

既有的本地链路分段（合成 Merkle 状态）作为对照基线；本实验补充真实链上状态 + 网络阶段，
使「证明占整个流程的比例」可在真实端到端条件下估计。

---

## 5. 与 MSM Phase D 的关系

- **Phase D（xyzz 桶 fill 内核）暂停**，不立即实施。本端到端实验先回答系统级问题：
  真实交易从输入准备到确认需要多久、资源峰值在哪里、Groth16 证明究竟占整个流程的多少。
- 前面完成的 MSM A–C 优化与源码剖析**全部保留**，作为对照基线；新的工作不改动生产实现，
  只在 Zebra + Zallet 提供的能力内做测量与剖析。

---

## 6. 最终结论

- 当前研究目标明确为**端到端 Testnet 交易流程**的耗时与内存剖析；
  **本地证明生成分段计时是其中的关键子段，而非全部**。
- 不能只完成本地构造便宣布交易流程研究完成——端到端必须覆盖广播、确认与钱包识别。
- 技术路线以 **Zebra + Zallet（Testnet）** 为优先；先做一笔功能验证，再开展重复测量。
- 先把这个端到端实验做扎实，再根据结果决定是否值得扩展或回头做 MSM Phase D 微优化。
