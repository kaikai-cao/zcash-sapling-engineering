--- 为什么需要这份文件 ---
正式 run 的 meta.json 中 binary_sha256 = null：执行时两个二进制都不在 PATH 上，
执行器的自动采集失败（与 2026-10-29 首轮采集失败同一原因）。RESULTS.md 早期版本把
ENV_binaries.txt（2026-10-29 采集）的两个哈希写成「本轮实测补录」——那是不准确的：
它证明的是「10-29 那天磁盘上的文件是这份」，并不直接证明「10-30 20:11 那次运行加载的
正是这份」。本文件把证据等级如实拆开，并补做了一次可核对的进程级采集。

--- 关键结构事实（决定了 pid 能不能用） ---
snapshot_restore.sh 每轮都杀旧进程再拉起新进程：
  L178-186  kill -TERM / -9 匹配 "zallet-zaino" 与 "$PREFIX/bin/zebrad"
  L207-215  setsid nohup zebrad ... / setsid nohup zallet-zaino ...
因此 meta.json 的 pids = {"zebrad": 5036, "zallet": 5341} 只代表**首轮**；
末轮 pid 在运行时已被替换。这也是为什么"直接读 meta.pids 的 /proc"当初不可行。

--- 五、复现命令 ---
# 磁盘文件
for f in zebrad zallet zallet-zaino; do
  printf '%-14s ' "$f"; sha256sum /home/dell/z3-regtest/bin/"$f" | cut -d' ' -f1
  stat -c '               bytes=%s mtime=%y' /home/dell/z3-regtest/bin/"$f"
done

# 存活进程的真实 exe
for name in zebrad zallet-zaino; do
  pid=$(pgrep -x "$name" | head -1)
  printf '%-14s pid=%s exe=%s sha256=%s\n' "$name" "$pid" \
    "$(readlink -f /proc/$pid/exe)" "$(sha256sum /proc/$pid/exe | cut -d' ' -f1)"
done

--- 六、已知限制（保持不变） ---
* 执行器的 binary_sha256 采集依赖 PATH，本环境两个二进制均不在 PATH 上，故为空。
* 采集时刻距离 run 结束 26 分钟；期间未重启节点（启动时刻仍为 20:41:11/18），
  故 /proc/PID/exe 仍指向 run 末轮加载的那份文件。
* zallet（launcher）只做 dispatch，实际参与测量的是 zallet-zaino；
  版本声明必须绑定后者，见 ENV_binaries.txt「关键结构发现」。
